# Pipeline

Individual tree detection from high-resolution drone orthomosaic imagery. The model
detects tree crowns as bounding boxes; each box centroid is exported as a single POINT
in EPSG:32617 for GIS use.

This document describes the **champion path** — the configuration that produces the best
result.

---

## 1. Overview

```
survey GeoTIFF ──► chip ──► split ──► train ──┬──► detect (region) ──► benchmark
                    │         │        │      │
                    │         │        │      └──► detect (full) ──► deliverable map
                    │         │        │
                    └─────────┴────────┴────────── config.yaml
```

Every stage reads the **same YAML config file**. A run is defined entirely by its config;
the scripts themselves do not change between experiments.

---

## 2. Requirements

- Python 3.10
- `ultralytics` (a version that recognises the YOLO26 weight strings)
- `torch` with CUDA support matching the target GPU
- `rasterio`, `geopandas`, `shapely`, `numpy`, `pillow`, `scipy`, `pyyaml`, `torchvision`

Model weights are downloaded on first use. On clusters where compute nodes have no
outbound network access, pre-fetch them from a login node:

```bash
python -c "from ultralytics import YOLO; YOLO('yolo26s.pt')"
```

## 4. Scripts

| Script | Role |
|---|---|
| `config.py` | Shared loader, imported by the stages below; not run directly |

| `split_dataset.py` | 80/20 train/val split, fixed seed |

`yolo_dataset/dataset.yaml` is also required; it is generated rather than tracked (see §8).

## 5. Configuration

A config file is the complete specification of a run.

```yaml
name: champion_5cm_5m

data:
  survey: ./download/umgables_2025/umgables_2025_drone_survey_5cm.tif
  survey_gtregion: ./download/umgables_2025/umgables_2025_drone_survey_5cm_gtregion.tif
  trees: ./download/um_gables_trees.geojson
  out_size: 640        # every chip is emitted at this pixel size
  ground_m: 32.0       # every chip covers this much ground
  radius_m: 5.0        # fixed crown box radius applied to every tree
  bg_ratio: 3          # keep 1 background chip per N tree chips

model: yolo26s.pt

train:                 # passed straight through to model.train(**train)
  data: ./yolo_dataset/dataset.yaml
  epochs: 200
  patience: 50
  imgsz: 1280
  batch: 16
  device: 0
  amp: true
  degrees: 180.0       # aerial imagery has no canonical orientation
  flipud: 0.5
  fliplr: 0.5
  scale: 0.6
  mixup: 0.1
  project: ./runs
  name: train1

detect:
  imgsz: 1280
  nms_iou: 0.5
```

Notes:

- `overlap_m` defaults to `radius_m` if omitted.
- The crown box in output-chip pixels is derived once in `config.py`:
  `radius_m / ground_m * out_size`. At 32 m / 640 px this gives 100 px for a 5 m box.
  The chipper and both detectors read that single derived value, so their tiling geometry
  cannot disagree.
- Everything under `train:` is forwarded verbatim to the training call. Nothing is added
  implicitly, so any parameter left out keeps the framework default.
- The config file is copied into the run output folder as `run_config.yaml`, making each
  run self-documenting.

### What config alone can change

Source resolution, crown box size, model architecture, any training hyperparameter, chip
geometry, detection NMS threshold.

### What requires a code change

Anything that alters *how labels are constructed* — per-species or per-tree box sizes,
taxonomic grouping, training on a subset of trees. These change the chipper's label loop
rather than a parameter. Prefer adding a parameter over forking the script.

## 6. Constant-input chip design

Every chip is emitted at a fixed pixel size covering a fixed ground footprint,
regardless of source resolution. A window of `ground_m / pixel_size` source pixels is
read and resampled to `out_size`.

| Source resolution | Source px read | Emitted | Effective detail |
|---|---|---|---|
| 5 cm | 640 | 640 | native |
| 7.5 cm | 427 | 640 | upsampled |
| 10 cm | 320 | 640 | upsampled |
| 20 cm | 160 | 640 | heavily upsampled |

This matters. An earlier design let the model input scale with source resolution, which
normalised detail away at the input layer and produced flat, uninformative results across
resolutions. The constant-input design isolates image detail as the only variable and
yields a clean monotonic ordering. **Any future resolution comparison must use this
design.**

Tile overlap is specified in metres, not pixels, so it is resolution-independent.

## 7. Evaluation region

The ground-truth point layer does not cover the entire survey. Large unlabelled areas
contain real trees the model correctly detects; scored against the full survey, those
correct detections count as false positives and understate precision for every model.

The fix: a polygon covering only the labelled area. The survey is clipped to it, ground
truth is clipped to it, and all benchmarking happens inside it. Pixels outside are zeroed,
and the detector skips near-empty tiles, so unlabelled regions produce no detections.

Effect on the champion: F1 0.615 → **0.660**, entirely through precision (recall
unchanged).

**All benchmarking is performed on the evaluation region.** A full-survey score is not
comparable to any figure here. The deliverable map, by contrast, is produced across the
full survey — the region is an evaluation construct, not an output boundary.

## 8. Running the pipeline

Chip and split:

```bash
rm -rf ./yolo_dataset
python scripts/chip_data.py ./configs/champion_5cm_5m.yaml
python scripts/split_dataset.py
```

The chipper prints its resolved geometry — source resolution, window size, emitted chip
size, crown radius in pixels. **Read this line.** It confirms which config actually ran.

`dataset.yaml` lives inside `yolo_dataset/` and is removed by the wipe. Recreate it:

```yaml
path: /absolute/path/to/project/yolo_dataset   # absolute path required by the framework
train: images/train
val: images/val
nc: 1
names: ["Tree"]
```

Train (on a GPU; submit as a batch job on a scheduled cluster):

```bash
python scripts/train_yolo.py ./configs/champion_5cm_5m.yaml
```

Detect over the evaluation region for benchmarking (GPU). A low confidence floor lets one
detection run cover an entire threshold sweep:

```bash
python scripts/detect_gtregion.py ./configs/champion_5cm_5m.yaml <weights> 0.05
```

Benchmark (CPU) across operating points:

```bash
for c in 0.05 0.075 0.10 0.125 0.15 0.20 0.25; do
  echo "conf $c"
  python scripts/benchmark_gtregion.py ./output/tree_detections_gtregion.geojson 5.0 $c
done
```

Produce the deliverable map across the full survey (GPU, several times as many tiles —
submit as a batch job):

```bash
python scripts/detect_full.py ./configs/champion_5cm_5m.yaml <weights> 0.15
```

The two detectors write different filenames, so a full-survey pass cannot overwrite the
detections a recorded benchmark was computed from.

## 9. Benchmark method

Point-distance matching against the ground-truth point layer:

- Detections sorted by descending confidence
- Each detection claims the nearest unclaimed ground-truth point within the match radius
  (default 5 m), via a KD-tree
- One-to-one; a ground-truth point cannot be matched twice
- Polygon inputs are reduced to centroids, so alternative detectors can be scored on the
  same footing
- All geometry reprojected to a common CRS

Reported: true positives, false positives, false negatives, precision, recall, F1.

The confidence floor filters detections *before* scoring, so a single low-confidence
detection run supports the full sweep. **Confidence does not change the model** — it
selects an operating point. Models must be compared each at its own peak-F1 confidence.
For the deliverable map the operating point has to be chosen at detection time instead,
which is why `detect_full.py` defaults to the champion's peak-F1 confidence rather than a
sweep floor.

## Appendix: known rough edges

- `split_dataset.py` is not config-driven — fixed seed, fixed ratio, deliberately never
  varied to preserve comparability across all runs.
- `crop_to_region.py` is not config-driven; survey paths are set in the file.
- `dataset.yaml` requires an absolute path; this is a framework limitation and the only
  exception to the relative-path rule.
- Tiling appends a final row and column offset flush to the raster edge. When raster
  dimensions leave a short remainder, these overlap their neighbours heavily and duplicate
  edge trees in the label set. Worth noting when a box count deviates from expectation.
